# Защита диктофона при потере или краже

Дата проверки: 2026-09-25. Это описание текущих границ защиты и план следующих
изменений, а не заявление о полной защищённости устройства.

## Что изменено сейчас

Setup разделён на Wi-Fi, «Настройки сервера» и VPN. Имена сохранённых Wi-Fi
сетей остаются видимыми по решению владельца. Пароли сетей не выдаются.

GET /config больше не возвращает адрес голосового сервера, адрес и маску VPN,
endpoint, порт, keepalive, NTP, публичный или приватный ключ, PSK и токен.
Для этих полей возвращаются только признаки наличия. Остаются имена Wi-Fi,
локальные IP, состояние соединения, переключатель VPN и таймер сна.
Значения не спрятаны CSS: их нет в JSON. Ответы /config и HTML имеют no-store.

Пустые поля оставляют значения на устройстве. Заполненные поля заменяют их;
PSK удаляется отдельной галочкой, все настройки — общим подтверждённым сбросом.
После успешного сохранения введённые значения очищаются из полей страницы.
Это не обещает стирания копий в памяти браузера, DevTools или автозаполнении.

При изменении gateway_url API требует явно передать токен: иначе старый bearer
можно было бы переслать на сервер атакующего. Интерфейс требует токен при любом
вводе адреса, потому что прежний адрес ему неизвестен. Изменения сохраняются
из временной копии лишь после общей валидации.

POST /config требует X-Hermes-Setup: 1, сброс — X-Hermes-Reset: confirm.
Это блокирует обычные cross-origin HTML-формы при отсутствии CORS.
Заголовки не являются паролем и не защищают от клиента в локальной сети,
DNS rebinding или физического владельца устройства.

## Что остаётся уязвимым

- Setup доступен клиентам AP и локальной Wi-Fi подсети без аутентификации.
  Можно менять настройки и сбрасывать устройство. Само сокрытие значений этого
  не исправляет.
- AP сейчас открыта; setup работает по HTTP. Вновь вводимые пароли и ключи
  передаются по этому каналу. Защита GET не шифрует POST.
- Настройки хранятся в NVS. В текущем sdkconfig.sticks3 выключены Secure Boot,
  Flash Encryption и NVS Encryption. Таблица разделов не содержит nvs_keys.
  Поэтому возможное чтение flash следует считать компрометацией Wi-Fi паролей,
  VPN ключа и токена. eFuse реального чипа отдельно не аудировались.
- Готовый диктофон можно использовать как владельца: отправлять записи,
  обращаться к агенту и получать ответы. Шифрование flash не остановит такое
  использование уже работающей прошивки.
- Возможности через VPN определяет серверный firewall. Полный туннель на клиенте
  не должен означать доступ ко всей домашней сети.
- Проверка нового gateway_url не закрывает подмену DNS, перенастройку VPN или
  перехват HTTP после отключения VPN. Нужна аутентификация настройки и сервера.
- Сброс через NVS не является гарантированным физическим стиранием старых flash
  страниц; удалённое стирание не гарантируется, если устройство выключено.

## Рекомендуемый порядок работ

1. **Отзыв и минимальные права на сервере.** У каждого диктофона собственные
   токен и WireGuard peer. Дать владельцу отдельную команду «потерян»,
   отзывающую оба доступа. Ограничить peer firewall-правилами до голосового API
   и действительно нужных сервисов. Запретить SSH, панели управления и прочую
   LAN. Не полагаться на клиентский AllowedIPs как на серверный firewall.
   Добавить квоты и аудит по device_id; голосовые запросы не должны получать
   права администратора, произвольного выполнения кода или удаления vault.
2. **Пароль владельца для настройки.** Один отдельный секрет владельца,
   не device token. Полный setup остаётся доступным и через локальную сеть,
   но после входа. Короткая сессия, лимит попыток, защита всех API, сканирования
   и сброса. Код, постоянно показываемый на украденном экране, не является
   доказательством владения. Восстановление пароля — только с уничтожением
   старых учётных данных и повторной привязкой.
3. **Защищённое первичное подключение.** WPA2-пароль точки доступа, создаваемый
   для сессии настройки и включённый в QR, ограниченное время работы AP.
   Это защищает от случайного соседа, но не от вора, видящего экран.
   Для настройки через LAN нужен HTTPS с проверкой подлинности устройства или
   проверенный протокол secure provisioning. Не придумывать собственную криптографию.
   Браузерный captive portal и доверие сертификату требуют отдельного прототипа.
4. **Аутентификация голосового сервера.** HTTPS с проверкой сертификата или
   закреплённого ключа; при необходимости mTLS. Проверить все операции протокола,
   включая polling и скачивание аудио, поведение времени и ротацию сертификатов.
   Нельзя отключать проверку сертификата ради удобства.
5. **Защита украденного работающего устройства.** Привязка к телефону владельца
   с криптографическим подтверждением либо разблокировка после включения.
   Короткая серверная аренда доступа ограничит работу после потери, но не отменяет
   необходимость отзыва. Простая проверка имени Wi-Fi или Bluetooth MAC ненадёжна.
6. **Защита flash.** Secure Boot v2 + Flash Encryption в release-режиме +
   NVS Encryption, уникальные ключи устройств, ограничения JTAG/download.
   Сначала испытать на запасном устройстве: подписанное обновление, восстановление,
   отключение питания и потеря ключей. Подготовить защищённое хранение ключа подписи.
   Текущая таблица содержит только factory app: до закрытия USB-разработки нужен
   проверенный путь обновления/восстановления, например подписанное OTA с rollback.
   eFuse могут изменяться необратимо — это отдельная миграция, не часть UI-патча.

Рекомендация: сначала пункты 1–3, затем серверный TLS и аппаратная защита.
На основном диктофоне eFuse и схема загрузки этим изменением не меняются.

## Что делать при потере прямо сейчас

1. На сервере удалить запись device_id потерянного диктофона из
   VOICE_DEVICE_TOKENS и пересоздать backend с обновлённым окружением.
   Сейчас карта токенов читается при запуске в backend/src/voice_gateway/app.py:
   редактирования env без перезапуска недостаточно. Проверить, что старые
   учётные данные получают 401, не выводя сам токен в журнал или shell history.
2. Удалить соответствующий WireGuard peer на VPN-сервере и из его постоянной
   конфигурации. При управлении через панель сделать это через панель, чтобы
   peer не вернулся при перезапуске. При прямом управлении механизм —
   wg set <interface> peer <public-key> remove. Проверить отсутствие peer.
   Остановка соединения на диктофоне не заменяет серверный отзыв.
3. Если возможно чтение памяти, считать сохранённые Wi-Fi пароли раскрытыми:
   сменить их, а также токен и ключи перед повторным использованием найденного
   устройства. Проверить последние задания/изменения Obsidian и остановить
   подозрительные уже запущенные задания: отзыв запрещает новые запросы,
   но не отменяет работу, уже поставленную в очередь.
4. Не рассчитывать, что удалённая команда стирания дойдёт до потерянного устройства.

Ни токены, ни VPN peer, ни пароли живого окружения этим патчем не отзываются.

## Проверка текущего изменения

Native-тесты проверяют отсутствие значений в сериализаторе статуса,
сохранение пустых полей, замену токена вместе с адресом, удаление PSK.
JS-тесты проверяют вкладки, сохранение без повторной передачи скрытых настроек,
игнорирование значений даже из старого JSON и существующий сканер Wi-Fi.
Страница проверяется в браузере на синтетических данных; реальный setup после
прошивки нужно проверить с телефона в сети диктофона.
