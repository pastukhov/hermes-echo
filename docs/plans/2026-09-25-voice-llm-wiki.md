# План: голосовой поток мысли → Obsidian → LLM Wiki → реализация идеи

Дата: 2026-09-25. Статус: предложение для обсуждения, реализация не начата.

## Результат для пользователя

Пользователь наговаривает мысль без подготовки. Система сохраняет исходник,
оформляет мысль по-русски, связывает её с накопленными знаниями в Obsidian и
коротко сообщает результат. Следующая запись может дополнить прежнюю идею.
Отдельная команда «составь план» или «реализуй идею …» переводит материал в
спецификацию или задачу разработки. Обычная диктовка не запускает разработку.
Это предлагаемое поведение по умолчанию, его можно изменить при обсуждении.

## Исследование и выбор основы

### LLM Wiki

Оригинал: [Karpathy, LLM Wiki](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f).
Это описание подхода, а не готовая библиотека: исходные материалы отделены от
поддерживаемой агентом базы знаний. Новые материалы должны обогащать связанные
страницы; нужны операции добавления, вопросов к базе и проверки её связности.

[andresbuonaiuto/cerebro](https://github.com/andresbuonaiuto/cerebro), MIT,
проверенный HEAD `d52cbffd8e795a1297a1cc2b8914c61f671432f3`.
Изучены README и [BLUEPRINT](https://github.com/andresbuonaiuto/cerebro/blob/d52cbffd8e795a1297a1cc2b8914c61f671432f3/BLUEPRINT.md).
Подходит как основа устройства vault и редакционных правил: страницы источников,
понятий и обобщений, ссылки на происхождение утверждений, явные противоречия,
индекс и журнал. Адаптировать эту логику для личной диктовки; не переносить
требование обсуждать каждое добавление и не устанавливать целиком чужой skill.

[ddsyasas/llm-wiki](https://github.com/ddsyasas/llm-wiki), MIT,
проверенный HEAD `e8dd69ebba0dc7c395c1b8217bb1c30c14e8c84c`.
Изучены `packages/core/src/ingest.ts` и `packages/core/src/prompts/ingest.ts`:
подбор связанных страниц, структурированный результат с новыми страницами и
обновлениями, разделение подготовки изменений и их применения. Заимствовать
эту архитектуру и адаптировать схемы/промпты в существующий Python backend.
Не добавлять отдельное приложение Next.js и второй самостоятельный сервер wiki.
При переносе кода или текста сохранить MIT notices и указать исходный commit в
THIRD_PARTY_NOTICES. До переноса проверить LICENSE именно закреплённой версии.

### Ramble your idea, then build

Найден [пост Карпатого о ramble sessions](https://x.com/karpathy/status/2079610838143623371).
Прямое чтение X недоступно; текст найден в поисковой копии зеркала. Он описывает
длинный свободный голосовой ввод и уточнение замысла через диалог. Отдельная
официальная реализация Карпатого под точным названием «Ramble your idea, then
build» не найдена. Не приписывать ему сторонние программы или нашу схему задач.

[BerkeleyHCI/Rambler](https://github.com/BerkeleyHCI/rambler),
HEAD `a293477086951144f20716a9959b6189dd3ee2b4`,
[исследование CHI 2024](https://arxiv.org/abs/2401.10838).
Это самостоятельная, более ранняя работа, а не реализация поста Карпатого.
Полезна логика превращения речи в смысловые фрагменты и их последующей правки.
Проверены README и server/server.js. Лицензия в дереве репозитория не обнаружена:
код не копировать до выяснения разрешений, использовать концепцию.

[nfarina/ramblr](https://github.com/nfarina/whisper-dictate), MIT по README:
пример диктовки контекста для работы с агентом. Полезный принцип — не терять
оговорки и сомнения при подготовке текста. Перенос macOS-приложения не нужен,
поскольку у нас уже есть диктофон, транспорт и STT. Этот проект не предоставляет
готовую цепочку Obsidian → wiki → разработка.

Решение: использовать cerebro как методическую основу, архитектуру ingest из
llm-wiki как образец реализации и подход Rambler к обработке потока мысли.
Объединяющий конвейер и запуск разработки реализовать внутри Hermes Echo.
Эти проекты изучены как исходники и документация; локальный запуск не выполнен.

## Что уже есть и чего не хватает

- `backend/src/voice_gateway/pipeline.py`: STT → агент → TTS, архивирование.
  Поле `note` валидируется и архивируется, но NoteStore в этом пути не вызывается.
  Транскрипт записывается лишь после успешного TTS: сбой озвучивания мешает
  сохранению уже полученного текста. Сохранение следует перенести раньше.
- `backend/src/voice_gateway/notes/note_store.py`: атомарная запись одной Markdown
  заметки с frontmatter; можно переиспользовать части, но отсутствует обновление
  нескольких связанных страниц с восстановлением после сбоя.
- `agent_service/codex_voice/service.py`: контракт короткого ответа и одной
  необязательной заметки; runtime работает в read-only. Для wiki нужен отдельный
  контракт обработки знания, а запись должен выполнять контролируемый backend.
- `docker-compose.yml`: `/data/obsidian` — named volume. Это ещё не подтверждённая
  связь с vault, который пользователь открывает в Obsidian.
- Запись ограничена 120 секундами (`firmware/include/button_driver.h`), приём —
  3 840 000 байт (`jobs/store.py`): 120 секунд PCM 16 кГц, mono, 16 bit.
- Общий deadline конвейера — 180 секунд; большую компиляцию wiki нельзя навсегда
  привязывать к ожиданию голосового ответа и состоянию подключения диктофона.

## Предлагаемая структура внутри существующего vault

Пользователь указал vault: `/home/artem/repos/obsidian`. Каталог и `.obsidian/`
проверены. Предлагаемый каталог интеграции: `/home/artem/repos/obsidian/Hermes/`.
При реализации подключить этот vault вместо отдельного Docker named volume,
сохранив существующее содержимое. Само подключение пока не изменено.

```text
Hermes/
  schema.md                 # правила оформления и обновления базы
  index.md                  # навигация
  log.md                    # журнал завершённых изменений
  sources/<capture-id>.md   # неизменённая расшифровка, время, ссылка на аудио
  ideas/<idea-id>.md        # оформленная мысль, статус, источники
  wiki/concepts/            # накопленные знания по темам
  wiki/entities/            # люди, проекты, инструменты по необходимости
  wiki/syntheses/           # выводы из нескольких источников
  builds/<build-id>.md      # спецификация, ход реализации, результат
```

Названия страниц на русском, стабильные ID независимы от заголовка. В frontmatter:
`id`, `type`, `created`, `updated`, `sources`, `tags`, `status`. Ссылки — обычные
Obsidian `[[...]]`. Аудио остаётся в серверном архиве; если нужно прослушивание
из Obsidian, согласовать каталог вложений и политику хранения до реализации.
Не импортировать автоматически все личные заметки и не переписывать их.

## Этапы реализации

### 1. Надёжно сохранить одну мысль

Подключить выбранный vault. Сразу после STT сохранять исходный текст со стабильным
capture_id/request_id. Подготовить структуру идеи: суть, контекст, детали,
ограничения, варианты, открытые вопросы, следующий шаг. Не заполнять пустые
разделы выдуманными фактами. Сомнения, отрицания, числа и самокоррекции сохранять.
Одна запись может содержать несколько идей, связанных с одним источником.

Backend проверяет схему и пишет файлы; голосовое «сохранено» формирует только
после подтверждённой записи. Ошибка TTS не отменяет заметку. Повтор запроса не
создаёт дубль. Исправление пользователя добавляет новый источник, не меняет сырой.

Критерий: запись с устройства появляется в настоящем Obsidian с исходником и
оформленной мыслью; отключение TTS и повтор запроса не теряют и не дублируют её.

### 2. Компиляция связанной wiki

Добавить `knowledge/` в backend: модели результата, выбор контекста, компилятор,
хранилище, проверка связей. По индексу/полнотекстовому поиску выбирать связанные
страницы в пределах бюджета контекста; перед изменением читать полное содержимое
выбранных страниц, а не перезаписывать их по обрезанному фрагменту.

Агент возвращает предложение изменений: новые страницы, обновления, источники,
связи и противоречия. Writer проверяет допустимые пути, ID, ссылки, источники и
хеш прочитанной версии. Ручная правка в Obsidian вызывает повторное согласование
изменений, а не молчаливое затирание. Единственная очередь записи на vault,
журнал транзакций, временные файлы и восстановление незавершённого применения.
Не обещать атомарность группы файлов одним os.replace: он атомарен для файла.

Личные планы и гипотезы маркировать как таковые. Повторение мысли не превращает
её в подтверждённый внешний факт. При противоречии сохранять обе версии и дату;
явную новую позицию пользователя помечать как заменяющую прежнюю.

Критерий: две записи на одну тему обновляют одну связанную страницу; проверяются
ссылки на оба источника, различие версий и восстановление после остановки worker.

### 3. Голосовые продолжения и вопросы к базе

По умолчанию диктовка сохраняет мысль. Команды «дополни предыдущую», «исправь…»,
«что я думал о…», «составь план…» имеют отдельные операции. Явный вопрос не
превращать автоматически в новую идею. Держать active_idea_id и сессию в БД,
а не полагаться только на историю разговора агента. При нескольких возможных
целях задать один короткий вопрос; исходную запись сохранить сразу.

Ответы по базе опираются на её страницы и источники. Новые выводы агента явно
отделены от слов пользователя. На устройстве звучит короткий результат; полное
содержание и ссылки остаются в Obsidian.

### 4. Длинный поток мысли

Поднять согласованные лимиты до 10 минут: 19 200 000 байт PCM плюс WAV overhead
там, где он применим. Проверить ограничения STT, таймауты HTTP, отмену, обрывы
мобильной сети и расход памяти. Поток не накапливать целиком в RAM устройства.
Продумать режим «нажать — начать, нажать — закончить», не конфликтующий с setup
и сном; сохранить привычный push-to-talk. Длительная wiki-обработка продолжает
работать в устойчивой очереди после отключения устройства.

Разделить состояния «исходник сохранён», «заметка готова», «wiki обновлена»,
«ошибка обработки». Быстрое подтверждение допустимо только для реально
завершённого этапа. Повторная доставка подтверждения не повторяет ingest.

Критерий: реальная запись 5–10 минут через мобильную точку и VPN; отсутствие
перезагрузок, обрезания мысли и дублей. Offline-запись при полном отсутствии сети
не входит в первую версию, для неё отдельно нужны локальное хранение и доставка.

### 5. Из идеи в реализацию

Команда «составь план по идее …» создаёт в Obsidian спецификацию: проблема,
желаемый результат, ограничения, нерешённые вопросы, критерии готовности, шаги.
Каждое существенное требование связано с исходной мыслью; предположения помечены.

Явная команда «реализуй …» запускает устойчивую build-задачу после определения
целевого репозитория. Исполнитель работает в отдельном checkout, фиксирует
результат и проверки. Заметка builds содержит состояние, ссылку на commit/PR и
следующий шаг. Автоматическое развёртывание не подразумевается. При неясной цели
нельзя угадывать репозиторий. Для идей без программного результата сначала
сформировать подходящий план, а не создавать код ради самого кода.

### 6. Проверка и ввод в эксплуатацию

- Детерминированные тесты writer: повторы, одинаковые заголовки, параллельные
  записи, сбой между файлами, изменения в Obsidian, недопустимые пути.
- Контрактные тесты агента: пустая/невалидная выдача, отсутствующий источник,
  неподтверждённое утверждение, несколько идей, неоднозначное продолжение.
- Набор русских диктовок с числами, отрицаниями, поправками и противоречиями;
  ручная оценка сохранения смысла, а не только проверки JSON.
- Интеграционные проверки: TTS падает после сохранения, worker перезапускается,
  ответ теряется, устройство выключается после приёма записи.
- Проверка живого vault в Obsidian: заметки, frontmatter, переходы, граф связей.
- Аппаратная проверка длинной записи и голосовых команд через VPN.
- Перед включением в основной vault — прогон в тестовом каталоге и резервная
  копия затрагиваемых файлов. Существующие записи не мигрировать без отдельного
  решения. Историю приватного vault не публиковать в Git-репозиторий проекта.

## Порядок поставки и решения до старта

Первый законченный срез: этапы 1–2, короткая запись → исходник → идея → связанные
страницы → правдивое голосовое подтверждение. Затем продолжения и длинная запись,
после этого build-задачи. Каждый срез получает свои проверки и commit/push кода.

можно принять по этому плану. Код приложения, прошивка и конфигурация работающих
сервисов в рамках подготовки плана не меняются.
