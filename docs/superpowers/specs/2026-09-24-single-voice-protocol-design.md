# Единый протокол голосового запроса — техническое задание

**Статус:** черновик на review пользователя

**Дата:** 2026-09-24

**Область:** прошивка M5Stack StickS3, Voice Gateway, setup portal и документация

## Цель

Оставить один поддерживаемый протокол обмена голосовыми запросами между StickS3 и Voice Gateway. Пользователь не должен выбирать «v1» или «v2», знать формат API-пути либо гадать, какой токен вводить. Целевой контракт — существующий асинхронный job-протокол, который сейчас обслуживается маршрутами `/api/v2/voice/...`.

Переход не должен внезапно отключить уже прошитые устройства, использующие синхронный `/api/v1/voice/turn`.

## Текущее состояние и проблема

- Прошивка поддерживает два контракта. V1 отправляет аудио одним потоковым HTTP-запросом и ждёт WAV в том же ответе. V2 сохраняет запрос на сервере, получает `202`, проверяет состояние задачи и скачивает WAV отдельным запросом.
- V1 выбран по умолчанию в прошивке и при отсутствии `protocol_version` в NVS. Уже настроенное устройство может сохранять `protocol_version=1`.
- V2 поддерживает request ID, дедупликацию повторной загрузки, ограниченную очередь, восстановление queued-задач после рестарта и отдельные токены устройств.
- В setup portal пользователь видит выбор протокола, разные правила ввода Gateway URL и поле токена, хотя это детали API.
- Текущая документация противоречива по авторизации: глобальный `AuthMiddleware` проверяет `VOICE_API_KEY`, если он задан, тогда как v2 routes дополнительно проверяют `VOICE_DEVICE_TOKENS`. При заданном глобальном ключе v2-запрос потенциально должен пройти обе проверки одним заголовком `Authorization`, что не соответствует обещанию независимого per-device token.

## Решение

### Целевой контракт

1. V2 job-протокол становится единственным поддерживаемым контрактом для новой и обновлённой прошивки.
2. Устройство всегда отправляет потоковый PCM S16LE, получает подтверждение приёма, опрашивает статус и скачивает готовый WAV. Request ID остаётся стабильным при проверке результата после сетевого сбоя.
3. Per-device bearer token — единственная схема авторизации запросов устройства к v2 API. `VOICE_API_KEY` не должен добавлять вторую независимую проверку к v2-маршрутам.
4. V1 сохраняется только как временный compatibility route на период обновления устройств. Он не показывается в setup portal как альтернативный режим и удаляется после выполнения критериев вывода из эксплуатации.
5. Протокольные версии остаются внутренним термином API/разработки. Основная пользовательская инструкция описывает один поток: «адрес сервера + токен устройства».

### Пользовательский интерфейс

- Удалить переключатель `v1 / v2` из обычной страницы настройки.
- Показывать одно поле **«Адрес Voice Gateway»** с примером базового адреса, например `http://192.168.1.10:8080`. Пользователь не добавляет endpoint path.
- Показывать одно поле **«Токен устройства»** как обязательное для целевого протокола; сохранённое значение можно оставить без повторного ввода.
- Объяснить коротко: токен должен быть зарегистрирован в Voice Gateway для ID этого устройства. ID устройства показывается в setup/status UI и основан на Wi-Fi MAC; MAC сам по себе секретом не является.
- Ошибки настройки должны отличать пустой токен, некорректный базовый URL и отказ авторизации, не выводя сам токен.
- Для уже работающего открытого setup AP сохранить явные указания, что это локальная настройка и AP не предназначена для доступа из недоверенной сети.

## Функциональные требования

### Прошивка StickS3

- Новые defaults используют единственный целевой job-протокол; устройство строит upload URL из базового Gateway URL.
- `protocol_version` больше не предлагается в UI и не определяет ветку поведения в целевой прошивке.
- При загрузке старой NVS-конфигурации прошивка должна распознать сохранённый v1. Она не должна незаметно отправлять запрос по новому контракту без токена или терять Wi-Fi/Gateway настройки.
- До удаления v1 пользователь с legacy-конфигурацией получает понятный путь миграции: обновить прошивку, добавить token для устройства в gateway и сохранить конфигурацию. При отсутствии токена показывается actionable ошибка; бесконечные циклы перезагрузки запрещены.
- Существующие свойства v2 сохраняются: стабильный request UUID, ограниченный повторный poll/upload, отмена, NVS-восстановление активного turn, проверка статусов и WAV перед воспроизведением.

### Voice Gateway и авторизация

- V2 endpoints продолжают проверять пару `X-Device-Id` + bearer token по `VOICE_DEVICE_TOKENS`.
- Для v2 должен существовать ровно один эффективный auth check per-device. Наличие `VOICE_API_KEY` не должно требовать, чтобы device token одновременно совпадал с глобальным ключом.
- V1 compatibility route во время перехода сохраняет явно задокументированное поведение и может быть ограничен отдельной настройкой или trusted-network policy. Его доступность и auth должны быть проверены до релиза, а не предполагаться из имени `VOICE_API_KEY`.
- После периода совместимости V1 route, синхронный transport path, неиспользуемые настройки и связанные тесты удаляются.
- Невалидный либо неизвестный device token возвращает стабильный `401`; не раскрывает, зарегистрирован ли конкретный device ID.
- Секреты не попадают в логи, метрики, архивы или ответы API.

### Сохранение настроек и миграция

- Обновление прошивки не сбрасывает SSID, Wi-Fi пароль и адрес gateway.
- Если существующая запись NVS содержит `protocol_version=1`, обновление должно классифицировать её как legacy и запросить необходимую настройку для целевого протокола. Автоматически считать старый optional token допустимым per-device credential нельзя.
- Сохранение новой настройки атомарно: при ошибке NVS старые сохранённые параметры остаются пригодными для повторной настройки.
- До готовности token mapping устройство может оставаться в setup AP/retry flow; ошибка настройки не должна приводить к постоянной перезагрузке или к потере captive portal.

### Документация и эксплуатация

- README, русская и английская инструкции прошивки, протокольная документация и deployment guide описывают один поддерживаемый сценарий.
- Во время перехода отдельно помечается legacy v1: для каких старых прошивок он нужен, как долго поддерживается и что сделать для миграции.
- Указать, что gateway должен получить device ID и уникальный token этого устройства через `VOICE_DEVICE_TOKENS` до успешной авторизации.
- Исправить существующие утверждения о `VOICE_API_KEY` после определения фактических правил auth для v1 и v2.
- Runbook должен содержать проверку token mapping и диагностику `401` без публикации секретов.

## Контракты и инварианты

- Запись: mono PCM S16LE, 16 kHz; верхний предел — 3 840 000 байт.
- Upload идентифицируется UUID request ID; повтор с тем же ID и теми же байтами идемпотентен.
- Успешный upload возвращает `202` с `turn_id`, `request_id` и `queued` status.
- Устройство опрашивает status и скачивает WAV только после `ready`; невалидный HTTP status, JSON вместо audio или некорректный WAV не передаётся в playback.
- V2 turn и все операции чтения/отмены доступны только владельцу device ID.
- Целевой voice response: WAV PCM16 mono, 24 kHz.
- Ошибка сети не создаёт новый request ID для того же незавершённого аудио.

## Этапы вывода V1

1. **Устранить неоднозначность авторизации.** Определить и покрыть тестами, что v2 использует только per-device token; документировать переходное поведение v1.
2. **Подготовить совместимость.** Сначала выпустить gateway, сохраняющий v1 и v2, с исправленным v2 auth и учётом обращений к v1 без логирования секретов.
3. **Мигрировать устройство.** Добавить token mapping для конкретного device ID, обновить прошивку, сохранить Wi-Fi/Gateway/token и подтвердить end-to-end голосовой turn через job-протокол.
4. **Переключить продуктовый путь.** Убрать выбор версии и разные правила URL из setup UI; сделать целевой протокол единственным штатным режимом.
5. **Вывести legacy route.** После периода наблюдения и подтверждения, что поддерживаемые устройства обновлены, удалить v1 маршрут и firmware path отдельным изменением.

V1 нельзя удалять в одном релизе с первым переходом: NVS и уже прошитые устройства могут продолжать отправлять старый контракт.

## Критерии приёмки

- Обычная настройка не содержит терминов v1/v2, protocol selector или endpoint path.
- Для нового устройства достаточно ввести Wi-Fi, базовый Gateway URL и зарегистрированный device token.
- Старый полный URL v1 не принимается как корректная новая конфигурация без понятного сообщения; существующая NVS-конфигурация при этом не стирается.
- V2-запрос проходит при настроенном per-device token независимо от наличия отдельного `VOICE_API_KEY`; неверный token даёт `401`.
- Legacy v1 продолжает работать в переходном релизе согласно явно заданной auth policy.
- Автоматические тесты покрывают старый NVS, отсутствующий/неверный token, повтор upload после потерянного ответа, длительную обработку, restart recovery, чужой turn, cancel и WAV validation.
- На физическом StickS3 проверены новая настройка, сохранение параметров после restart, успешный голосовой turn, сетевой сбой и восстановление без бесконечного reboot loop.
- Перед удалением v1 есть проверяемое основание считать legacy clients мигрированными; после удаления нет v1 route или скрытого firmware fallback.
- Обе языковые версии документации соответствуют реальному поведению и не обещают неподдерживаемую авторизацию.

## Не входит в эту задачу

- Новый автоматический enrollment/pairing service для выпуска device tokens.
- TLS, VPN или изменение сетевой модели Voice Gateway.
- Переработка STT, выбора Hermes/Codex, TTS, audio codec или формата архивирования.
- Автоматическое удаление или изменение сохранённого Wi-Fi пароля.

## Риски и открытые решения для реализации

- **Выдача токена:** текущая конфигурация требует вручную связать device ID и token в `VOICE_DEVICE_TOKENS`. Автоматическое сопряжение упростило бы первое подключение, но является отдельным проектом и требует отдельной модели авторизации.
- **Окно поддержки v1:** срок должен быть выбран перед релизом переходной прошивки; удаление зависит от фактических устройств, а не только от календарной даты.
- **Обратная совместимость настройки:** нужно зафиксировать точный UX для legacy NVS, особенно если Wi-Fi уже работает, а токена для v2 ещё нет.
- **Общий API key:** перед реализацией надо проверить все `AuthMiddleware` исключения и порядок middleware, чтобы v2 не оказался защищён одновременно несовместимыми глобальным и per-device секретами.
