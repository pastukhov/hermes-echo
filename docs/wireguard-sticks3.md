# WireGuard на диктофоне StickS3

## Выбор реализации

Подключена `esphome/wireguard` **0.4.6**, исходный тег `v0.4.6`, commit
`cddaa4eab4e633847bf846723ac0449a34c3d2f7`:

- [ESP Component Registry](https://components.espressif.com/components/esphome/wireguard/versions/0.4.6/readme)
- [Исходники](https://github.com/esphome-libs/wireguard/tree/v0.4.6)

Для этого проекта она предпочтительнее Arduino-обёртки
[ciniml/WireGuard-ESP32-Arduino](https://github.com/ciniml/WireGuard-ESP32-Arduino):
прошивка использует чистый ESP-IDF 5.5.3. Ветка ESPHome развивает
[trombik/esp_wireguard](https://github.com/trombik/esp_wireguard), поставляется
как компонент ESP-IDF и имеет compile-тест интеграции. Это выбор по совместимости
и сопровождению, а не результат сравнительного аудита криптографии или замера скорости.
Версия зафиксирована в `firmware/src/idf_component.yml`, зависимости и их хеши —
в `firmware/dependencies.lock`. Загрузка зависимостей выполняется при сборке.
Лицензия WireGuard-компонента — BSD-3-Clause; тексты лицензий входят в пакеты.

## Настройка

Подключитесь к setup AP диктофона и откройте `http://192.168.4.1/`.
Раздел **WireGuard VPN** находится перед кнопкой **Save & Restart**.
На питании USB автоматический сон отключён. Страница настроек доступна только
из setup-сети, как и раньше.

| Поле | Значение |
| --- | --- |
| Enable WireGuard | Включение клиента; по умолчанию выключен |
| VPN IPv4 address | Адрес самого диктофона, например `10.7.0.2` |
| VPN subnet mask | Маска VPN-подсети, например `255.255.255.0` |
| Server hostname or IPv4 | Только имя или IPv4 сервера, без схемы и порта |
| Server UDP port | Обычно `51820` |
| Peer public key | Публичный ключ сервера |
| Device private key | Приватный ключ, выделенный для диктофона |
| Preshared key | Необязательный PSK; должен совпадать на сервере |
| Remove saved preshared key | Явное удаление сохранённого PSK |
| Persistent keepalive | По умолчанию 25 секунд; 0 отключает keepalive |
| NTP server | По умолчанию `pool.ntp.org`; доступен до запуска туннеля |
| Full IPv4 tunnel | Разрешить `0.0.0.0/0` и назначить VPN маршрутом по умолчанию |

Пустые поля приватного ключа и PSK сохраняют прежние значения. GET `/config`
возвращает только признаки наличия секретов, а не сами ключи. При сохранении
проверяются base64-ключи длиной 32 байта, IPv4, непрерывная маска и диапазоны
числовых полей. Настройки хранятся в NVS и применяются после перезагрузки.
Это обычное NVS текущей прошивки, без добавления шифрования flash/NVS.

На сервере создайте отдельный peer с публичным ключом диктофона и
`AllowedIPs = 10.7.0.2/32`. Для его получения используйте обычные `wg genkey`
и `wg pubkey` у себя; прошивка не генерирует и не экспортирует приватные ключи.
В поле **Gateway endpoint** укажите VPN-адрес голосового сервера: например,
для протокола v2 `http://10.7.0.1:8080`, для v1 — полный путь запроса.

## Маршрутизация и ограничения

Поддерживается один peer и IPv4. В обычном режиме разрешена VPN-подсеть из
адреса и маски интерфейса. Например, `10.7.0.2` + `255.255.255.0` разрешают
`10.7.0.0/24`. Голосовой сервер должен находиться в этой подсети. Произвольный
список нескольких AllowedIPs в этой версии интерфейса не поддерживается.

Полный туннель разрешает все IPv4-адреса; сервер должен обеспечивать нужную
маршрутизацию/NAT. Прямые локальные маршруты Wi-Fi/setup AP остаются локальными,
это не режим полного запрета любого трафика вне VPN. IPv6 не туннелируется.
DNS берётся из существующей Wi-Fi-конфигурации; отдельного VPN DNS нет.

При включённом VPN голосовые HTTP-соединения дополнительно привязаны к
WireGuard-интерфейсу. Пока peer не поднят, начало записи и новые запросы
блокируются. Это не даёт голосовым соединениям автоматически переключиться
на Wi-Fi при удалении VPN-интерфейса. DNS и начальная синхронизация времени
могут использовать обычную сеть.

VPN-подсеть не должна пересекаться с Wi-Fi-подсетью или setup AP
`192.168.4.0/24`. При пересечении туннель не запускается.

## Состояния

Страница обновляет статус каждые 3 секунды, не перезаписывая редактируемые поля:

- `disabled` — выключен;
- `waiting_wifi` — ожидание Wi-Fi и IP-адреса;
- `waiting_time` — ожидание времени через NTP;
- `connecting` — интерфейс запущен, рабочего peer ещё нет;
- `connected` — библиотека подтвердила активную сессию peer;
- `subnet_conflict` — пересечение подсетей;
- `error` — некорректные настройки или ошибка запуска.

После потери Wi-Fi туннель удаляется, затем создаётся заново; ошибки создания
повторяются с паузой. Все операции raw lwIP выполняются на tcpip_thread,
стек которого увеличен до 8192 байт. Приватные ключи в лог не выводятся.

## Проверка

```sh
/home/artem/platformio/.venv/bin/platformio test -d firmware -e native
node --test firmware/test/web-ui.test.mjs
/home/artem/platformio/.venv/bin/platformio run -d firmware -e sticks3
```

Проверены валидация и декодирование формы, сохранение прежних секретов при
пустом вводе, явное удаление PSK, пределы числовых полей и веб-форма.
Сборка для ESP32-S3/ESP-IDF 5.5.3 прошла. Форма дополнительно просмотрена
в браузере на локальном preview с демонстрационными данными.

Для сквозной проверки нужны реальные параметры peer: после заполнения формы
проверить `connected`, свежий handshake на сервере, голосовой запрос,
восстановление после отключения Wi-Fi и отсутствие прямого голосового запроса
при недоступном VPN. Сам факт сборки и загрузки не подтверждает эти проверки.

Результат проверки 25 сентября 2026:

- Native: **57/57**, веб-форма: **9/9**.
- Образ занимает 1 141 241 байт flash и 116 340 байт статической RAM.
- Загрузка через `/dev/ttyACM0` прошла с `Hash of data verified`.
- После перезапуска serial показывает ESP-IDF 5.5.3, запуск settings UI,
  подключение Wi-Fi и получение адреса. За 30 секунд наблюдения panic/reset нет.
- SHA-256 ELF: `5184bfca43def120b0ec416cecedfe1bc5739a34ebb2e01396b6e2b1a0ace72c`;
  префикс в boot log совпадает.
- Из домашней LAN устройство отвечает ожидаемым `403 setup network only`.
  Реальная форма через setup AP в этом прогоне не проверялась: компьютер
  оставался в домашней сети. Проверка формы в браузере использовала preview.
- WireGuard оставлен выключенным. Реальные ключи/сервер не вводились;
  handshake, передача голоса по VPN и восстановление туннеля пока не проверены.
